Le lanceur canonique `scripts/start.cmd` exécute d'abord le lifecycle Orchestrator existant, puis `scripts/prod-edge-start.py`. Ce second programme démarre/réutilise uniquement la Gateway de maintenance 8510 et Caddy PROD 8501, et **n'invoque jamais ServerManager ni le serveur intégré PHP**. Il ne démarre pas le backend PROD 8511. Aucun fichier source `H:\EZScore` n'est modifié par le commit (la Gateway a déjà un état runtime `H:\EZScore\var\runtime\online-gateway.json`).

La Gateway est mise **en maintenance effective** avant le démarrage de Caddy, préservant l'accès public à la page de maintenance après arrêt total des processus. Le mode mémorisé est lu : si l'ancien mode était `normal`, ce mode n'est **pas encore restauré** car le backend FastCGI/HTTP de PROD n'est pas migré ; dans ce cas le lancement échoue fermé en maintenance avec `PROD_NORMAL_RESTORE_BLOCKED_BACKEND_MIGRATION_PENDING`. Une restauration fidèle de `normal`, l'état `arrêté` et les boutons UI restent des gates obligatoires. Cette étape privilégie la sécurité au retour prématuré de PROD normale.
